## 第 1 章 侦察：先搞清楚对象是什么

### 1.1 目标

在不动对方一个字节的前提下，先弄清四件事：

1. 进程结构（Electron 应用会有主进程 + 若干渲染进程，同名进程不止一个）
2. 安装目录与数据目录分别在哪、各放什么
3. 哪些文件是加密的、用什么后缀区分
4. **它自己有没有日志** —— 这一项性价比最高，很多问题能直接读出来

### 1.2 排查顺序（先看，再动手）

**① 进程与安装目录**

```bash
tasklist | grep -i <进程名>
```

> ⚠️ 同名进程会有多个（主进程 / GPU / 渲染 / 工具进程）。
> 后文凡涉及"对窗口操作"的地方，都必须能区分它们，否则会操作到错误的那个。

典型目录结构（Electron 打包后的形态）：

```
<安装目录>\
├─ <主程序>.exe                    ← Electron 主程序
├─ resources\
│  ├─ app.<打包后缀>               ← 打包后的应用代码（asar 变体，**单个文件**）
│  └─ dist\  res\  plugins\ ...    ← 渲染层资源（可能是密文）
```

**② 数据目录**（真正的业务数据在这里，通常与安装目录分离）

```
<数据目录>\
├─ <资源目录>\<ID>\...             ← 课程包（题目结构 / 答案 / 索引）
└─ logs\                           ← ★ 客户端自己的日志
```

**③ 读日志**（第一步就该做）

```bash
# 它请求了哪些域名、用了哪些接口、报了什么错，往往全在里面
grep -oE "https?://[^ \"']+" app.log | sort | uniq -c | sort -rn | head -20
```

> 这一步的产出是一张"它依赖哪些外部服务"的清单。**先有这张表，再决定后面做什么**，
> 而不是反过来——先决定做什么，再去猜它依赖谁。

**④ 给文件分类**（后缀 + 文件头两条线索）

```bash
find <数据目录> -name "*.<后缀>" | head
```

顺手看一眼**文件头**（能省几小时）：

```python
head = open(path, 'rb').read(16)
print(head.hex())      # 有魔数 → 可以立刻和其它格式区分开
```

## 第 2 章 观测手段：先建立可验证的通道

### 2.1 原则：**试探 + 看日志验证，而不是猜**

Electron 应用天然带两套原生调试通道：

| 通道 | 作用 |
|---|---|
| 渲染进程调试端口 | 暴露页面目标，可执行 JS、读 DOM，也能定位 iframe/frame 树 |
| 主进程 inspector | 暴露 Node 目标，可调用主进程能力（文件、原生模块） |

> **这类客户端常会把原生开关改名**（在原生层改名，JS 层看不到），因此不能照抄通用开关名。
> 正确做法是：**构造若干命名变体去试探，再用它自己的日志确认哪个真的生效**。
> 「试探 → 看日志 → 确认」这个循环，是后面所有工作的前提。

### 2.2 建立最小可用观测

**① 完全退出客户端（含托盘）**，再用带开关的命令行启动，避免多实例 / 残留。

**② 确认端口真的开了**（不要假设）

```bash
curl -s http://localhost:<端口>/json/list
# 渲染目标：每项带 webSocketDebuggerUrl
# 主进程目标：type 为 "node"
```

**③ 用最小依赖的方式执行 JS**

用原生 WebSocket 手写一个最小 CDP 客户端（不引第三方库）就够验证连通性：
握手 → 发 `Runtime.evaluate` → 收同 `id` 的响应。**先跑通一条最小链路，再往上加功能。**

**④ 关键坑：主进程目标的 `userGesture` 必须是 `false`**

调 `Runtime.evaluate` 时，页面目标可以 `true`，**Node 目标必须 `false`**，
否则会直接失败或行为异常。这种"少一个参数就静默失效"的地方在本领域非常常见——
**每加一个参数，都要问"它生效了吗、我怎么验证"。**

### 2.3 两套通道分别用来做什么

- **页面目标** → 读 DOM、判题、点击 → 第 9 章的页面自动化全建立在它之上
- **主进程目标** → 访问文件与原生模块能力 → 用于读取"打包后的应用代码"，见第 5 章的思路

## 第 3 章 文件格式识别

### 3.1 为什么要先做格式识别

同一个目录里可能混着**多种加密格式**。它们的差异不一定写在文件名上，
但几乎一定体现在**文件头与字节布局**上。先把格式分清楚，后面才不会把
"格式判断错"误判成"解密失败"。

### 3.2 判别思路

**① 找同类文件，对比头部**

```python
# 取若干样本的前 16/48 字节，观察：
#   有没有固定前缀（魔数）？
#   前缀长度是固定的吗？
#   去掉前缀后，剩余长度是不是"16 的整数倍 + 少量"？
```

**② 用布局反推格式**

典型的分块布局长这样（**具体偏移必须自己量，不要照抄**）：

```
[魔数 N 字节][附加段 M 字节][IV 16 字节][密文 ...]
```

关键判据是**长度关系**：密文长度是 16 的整数倍（CBC）或"加密文本长度 + 16"（GCM，末尾带 TAG）。

### 3.3 🔴 必须记住的一个危险模式：**"看起来很对"**

> **事故**：以为 IV 在某偏移，实际偏移比它大一个"附加段"的长度。
> 在 CBC 模式下，**只有第一个块是乱码，后面全部"看起来正常"**。
> 于是现象变成"有的文件解出来正常、有的开头乱码"，非常容易被误判成"密钥不对"。

**结论**：验收必须看**首块内容**，不能只看"有没有抛异常"、"长度对不对"。

- [ ] 解释"为什么把偏移搞错时只有首块乱码"

## 第 4 章 加密容器的解析原则

### 4.1 原则一：**内容验收，而不是 try/catch**

用错误密钥解 CBC+PKCS7 时，有约 **1/256** 的概率填充恰好合法（不抛异常）。
只靠 try/catch 判断，就会把随机噪声当明文写出去，然后花几小时排查"为什么是乱码"。

```csharp
/// <summary>内容验收：明文必须是可读文本（抑制"解错但没抛异常"的误报）</summary>
static bool LooksLikeContent(byte[] p)
{
    if (p.Length == 0) return false;
    int bad = 0;
    foreach (var b in p)
        if (b == 0 || (b < 0x09 && b > 0x0D)) bad++;
    if ((double)bad / p.Length > 0.05) return false;          // 控制字符过多 → 不是文本
    var head = System.Text.Encoding.UTF8.GetString(p[..Math.Min(64, p.Length)]);
    return head.TrimStart().StartsWith("{") || head.TrimStart().StartsWith("[")
        || head.Contains("function") || head.Contains("var ") || head.Contains("<");
}
```

> **判据要用内容特征（是不是文本 / 是不是 JSON），不要用异常。**
> 这条在本项目里反复出现：**"没报错"从来不等于"做对了"。**

### 4.2 原则二：多密钥候选 = 逐个试 + 用样本验收

如果有多个可能的密钥（例如格式新旧两套）：

```csharp
foreach (var k in Keys)
{
    try
    {
        var plain = AesCbcBytes(k, iv, ct, decrypt: true);
        if (!LooksLikeContent(plain)) continue;     // ← 关键：内容验收挡掉误命中
        return (k, Encoding.UTF8.GetString(plain));
    }
    catch { /* 换下一把 */ }
}
```

判定规则：**至少一份真实样本解出"像内容"的明文**，且同格式组成功率 ≥ 80%。
不要用"看着像 base64"当判据。

### 4.3 原则三：**只读原始文件、只写新文件**

```
✗ 覆盖客户端数据
✓ 解密结果写到自己的数据目录（新文件）
```

理由有两条，都很硬：
1. 对方可能有完整性校验，改动会被发现；
2. **改动即留痕**——一旦写坏，你连"还原到原状"都做不到。

### 4.4 批处理与三态统计

```csharp
int okA = 0, okB = 0, fail = 0;
foreach (var f in Directory.EnumerateFiles(root, "*.<后缀>", SearchOption.AllDirectories))
{
    try
    {
        var text = Decrypt(File.ReadAllBytes(f), out var key);
        if (key == Keys[0]) okB++; else okA++;
        File.WriteAllText(f + ".dec", text);          // 只写新文件
    }
    catch (Exception e) { fail++; Console.WriteLine($"[FAIL] {f} {e.Message}"); }
}
Console.WriteLine($"A={okA} B={okB} 失败={fail}");
```

**失败必须打印路径**——否则你不知道是"格式没覆盖"还是"真坏了"。

## 第 5 章 内容资源的密钥链（概念）

### 5.1 现象：密钥不在文件里

有些资源（图片/音频/资源包）在文件里**找不到密钥**——只有 IV、密文、TAG。
这是很典型的"**密钥不在文件里**"设计：密钥被**另一层加密后藏在索引文件里**，
而索引文件本身用另一套固定方案加密。

### 5.2 概念模型：三层嵌套

```
[索引文件]                ← 本身是另一种可解格式
        ↓ 解密得到 { 校验前缀, 混淆后的密钥串 }
        ↓ 去混淆 → 候选密钥
        ↓ 自校验（前缀与密钥的摘要比对，防止拿错）
   → 真正的内容密钥
        ↓
   用该密钥解内容资源：[IV][密文][TAG]
```

**这里最值得学的是那个"自校验前缀"设计**：把密钥的摘要放在数据里，
解密方先比对摘要再解密——**这样"拿错密钥"能被立刻发现，而不是解出乱码**。
自己做类似设计时，强烈建议照这个做。

### 5.3 最常见的坑：**必须逐级向上找**

索引文件与目标文件**不一定在同一目录**。正确的查找是**从目标目录逐级向上**：

```csharp
static string DeriveContentKey(string dir)
{
    for (var d = new DirectoryInfo(dir); d != null; d = d.Parent)   // ← 逐级向上
    {
        var idx = Path.Combine(d.FullName, "<索引文件名>");
        if (!File.Exists(idx)) continue;
        ...                                                          // 找到即推导
    }
    throw new FileNotFoundException("未找到索引文件");
}
```

> 只查同级目录 → **一半资源解不开**，而且报错是"密钥校验失败"，
> 极易误判成算法写错。**"找到的样本能解、其它的不能"这类现象，先怀疑查找范围。**

### 5.4 内容密钥会变 —— 所以不能缓存

索引文件会被客户端**定期重写**。因此：

> **内容密钥必须每次运行时重新推导，绝不能缓存进配置文件长期使用。**

这是"有期限 / 会被外部改动"的典型，处理方式见第 11 章。

## 第 6 章 数据格式解剖（题目从哪来）

### 6.1 数据来源的两种形态

| 形态 | 特点 |
|---|---|
| **A. 本地已缓存数据** | 全、稳、离线；缺点是"只有已加载过的内容" |
| **B. 运行时获取的数据包** | 能拿到尚未落盘的内容；缺点是依赖网络链路 |

工程上建议：**A 为主、B 为补充**，两者归一化成同一份内部模型。

### 6.2 XML 型课程包

```
<课程目录>\
├─ paper.xml            ← 试卷结构：题目在 <element type="3"> 节点
└─ correctAnswer.xml    ← 答案：按 <element id> 与题目关联
```

**读法要点（照做，别发明）**：

- 题目节点的判别靠 `type` 属性，不要靠顺序。
- **文本字段常包在 `CDATA` 里**——而且**同一个字段可能含多段 CDATA**。
  取正文必须**聚合全部**，用"取第一个"的写法会**静默丢内容**。
  这个坑很隐蔽：单段时看起来完全正常。
- **标签属性不一定紧跟标签名**。写解析时属性段要按"引号内不截断"匹配，
  不要假设"属性只有一个、且排在最后"。否则会**整条漏掉**某种形态。

> 这两条是同一类错误的两个面：**"可重复的容器"不能用单次匹配**。

### 6.3 JSON/JS 型课程包（绘本类）

题目通常在一个 JS 文件里以对象字面量形式给出，字段比 XML 型更自由：

- 题干可能是**字符串**，也可能是**对象**（带 `text` 字段）——两种都要兼容。
- 选项可能是数组，也可能嵌在子字段里（`questions_list` 之类）。
- **题型编号**要实测建立映射表，不要靠猜。

### 6.4 字段口径（逐字照抄，别猜）

| 概念 | 含义 | 常见坑 |
|---|---|---|
| 题干 | 问题正文 | 可能带 HTML 标签，入库前要清洗 |
| 材料 | 共享的阅读/听力原文 | 与题干是**两个**字段，不要混为一谈 |
| 选项 | id + 文本 | id 不一定是 A/B/C/D，也可能是 1/2/3/4 |
| 答案 | 选项 id **或**整段文本 | 非选择题（作文/续写）答案是长文本，不是 id |
| 解析 | 逐题解析 | 听力题的"解析"字段常装**听力原文**，长度可达上千字 |

> 🔴 **最后一行是个真实的设计陷阱**：如果界面上按"内容长度"决定排版，
> 把"解析"也算进判据，就会让**所有听力题**都走错分支。
> **判据的字段选择必须基于对数据的实测分布**，不能想当然。

## 第 7 章 答案解析与入库

### 7.1 从数据包到答案

答案的关联方式通常是**按题目 id**。要点：

1. **先建立 id → 答案 的映射**，再与题目 join。
2. **id 形式不固定**（可能是哈希串，也可能是序号），所以除按 id 外，
   还要准备**按题号**的回退映射。
3. **join 失败要有可诊断的兜底**：按顺序回退，并记录"用了哪种回退"。

### 7.2 字段优先级（照抄，别发明）

同一道题的信息可能来自多个来源（本地缓存 / 运行时数据包 / 手工补充）。
**必须定义明确的优先级**，并且**登记每条数据的来源**，否则出现分歧时无从判断。

### 7.3 入库与去重

- **归一化键**：文本归一化后再做键（见 8.1），否则"全角/半角/空格差异"会造成重复条目。
- **缓存键要覆盖"数据变化"**：新落盘的数据往往只改子目录的时间戳，
  只用顶层目录时间戳会导致**缓存不失效**。
- **外部补充的条目要能重放**：整库重建时不能丢（否则用户重启就没了）。

### 7.4 自检

- [ ] 题目与答案的 join 成功率可统计
- [ ] 重复条目数（按归一化键）为 0
- [ ] 数据变化后缓存确实失效

## 第 8 章 匹配算法（本类程序的核心竞争力）

### 8.1 文本归一化（一切的基础）

```csharp
public static string NormKey(string s)
{
    if (string.IsNullOrEmpty(s)) return "";
    var t = StripTags(s).ToLowerInvariant();
    return Regex.Replace(t, @"[^a-z0-9\u4e00-\u9fff]+", "");   // 只留字母数字与汉字
}
```

**为什么要这么狠**：真实数据里同一个句子会以"带空格 / 带标点 / 全角半角 / 多余换行"
等多种形态出现。**归一化不彻底，后面所有匹配都是带噪声的。**

### 8.2 双通道打分

题干与选项**分别打分再加权**，不要只比题干：

```
score ≈ 题干相似度 × 2 + 选项相似度 × 3
```

要点：
- 词元长度 > 3 才计入（太短的词元（如 "a"、"的"）噪声极大）
- 覆盖率门槛（如 0.6）：低于门槛直接判"未命中"，**不要给出低置信答案**
- 题干要求重合词 ≥ 2、选项要求命中 ≥ 2 —— 单点命中不足以定性

### 8.3 ★ 选项内容映射：为什么"顺序打乱"也能点对

这是整个方案里最关键的一个设计。

**问题**：题库里的答案记的是"原题里第几个选项"，但用户面对的卷面**选项顺序可能被打乱**。
直接按序号点 → 点错。

**解法**：**不按序号，按内容**。

1. 用题库里答案选项的**文本**，在当前题目的选项列表里找出**内容一致**的那一项；
2. 得到"当前卷面上它的位置"，再据此作答；
3. 找不到时**降级**（标记低置信并交给可诊断的兜底），而不是硬点一个。

> 这个设计让"选项顺序变化"从"致命问题"变成"无所谓"。
> **凡是能被外部打乱的东西，都不要依赖它的顺序。**

### 8.4 置信度门槛与"宁可不答，不要错答"

分级门槛（高/中/低）：

- **高**：多通道都命中且分数显著领先
- **中**：单通道命中但分数够
- **低**：仅勉强过门槛 → **默认不自动作答**，只提示

> 自动作答一旦答错，用户体验比"不答"差得多。**默认保守，把阈值开放给用户调。**

### 8.5 未命中也要可诊断

未命中时，日志里必须能区分：

- **缺数据**（题库里根本没有这道题）
- **算法不匹配**（有题但没匹配上）

**做法**：打印 Top-N 候选及其分数。若第 1 名分数接近门槛 → 是阈值问题；
若全部很低 → 是缺数据。**没有这个区分，你只会看到"命中率低"这一个无用的结论。**

### 8.6 自检

- [ ] 用真实卷面文本跑一遍，**逐条回验误报**（不能只验"该命中的命中了"）
- [ ] 故意打乱选项顺序，答案仍正确
- [ ] 未命中日志能区分"缺数据"与"不匹配"

## 第 9 章 页面自动化（CDP）

### 9.1 架构：一轮做什么

```
取快照 → 识别当前题 → 匹配答案 → 作答 → 确认状态变化 → 翻页/结束判断
```

每一轮都必须是**幂等**的：中途失败下一轮能接着做，而不是进入半成品状态。

### 9.2 附着：必须"试出来"，而不是"猜"

调试目标里可能同时存在页面、iframe、以及**壳页面**（`local://...?url=<编码地址>`）。
选择规则要**显式**：

- 排除已知的壳页面形态
- 优先匹配业务所在的目标
- **多个候选时把候选列表打出来**（出问题时你能立刻看出选错了）

### 9.3 帧树：一个"少剥一层"就全盘失效的坑

页面内容可能位于 **iframe（同源 / 跨域）** 或 **shadowRoot** 中。

**必须按帧树递归**取快照。跨域 iframe 需要**隔离世界（isolated world）**的方式访问。
只处理顶层文档 → 在嵌套页面上会**完全取不到内容**，而且症状是"像页面没渲染"。

### 9.4 快照脚本的设计要点

1. **递归**：文档 → iframe → shadowRoot
2. **只取可见且与视口相交的元素**（被 transform 推到屏外的常驻元素必须排除，
   否则会答到错误的题上）
3. **带上稳定的标识**：优先用元素自身的业务 id 属性，退而求其次用文本指纹
4. **不进 DOM 数据**：只读取，不修改页面结构（改结构会影响后续判定）
5. **超时与异常兜底**：快照脚本自身失败不能把整轮拖死
6. **结构签名**：连续 N 轮签名一致才认为页面稳定 —— **不要一有新内容就动手**
7. **排除"假变化"**：选中态、计时器文本这类每秒都在变的东西不能计入签名

### 9.5 作答：点击、填空、翻页

- **点击前先确认目标可点**（可见、在视口内、未禁用）
- **一轮内限制动作数**（如 ≤2 题），并加**随机停顿**（几百毫秒级）——
  固定节奏的机械化操作既容易被判定异常，也容易点到还没渲染完的元素
- **翻页成功以"内容变化"为准**，不要以"点了按钮"为准
- **结束页要能识别**（没有下一题 / 出现结算页）

### 9.6 循环间隔：不同类型的引擎**必须分开配**

> **事故**：DOM 路径与 OCR 路径共用一个轮询间隔 → 点击延迟在 0~20 秒随机浮动。
> 两条路径的合理节奏差一个数量级：DOM 可以秒级甚至亚秒级，OCR 必须给足渲染与识别时间。

**结论**：间隔按引擎分别配置，且都要有下限保护。

### 9.7 自检

- [ ] 帧树解析正确，嵌套页面也能取到内容
- [ ] 快照覆盖同源 iframe / shadowRoot
- [ ] 点击有节流、有防死循环、翻页以内容变化为准
- [ ] 结束页能识别
- [ ] DOM 与 OCR 间隔**分开配置**

## 第 10 章 OCR 降级路径（没有调试口时的保底）

### 10.1 定位

自动化路径依赖调试通道；**通道不可用时必须有降级路径**：
截屏 → OCR → 按坐标点击。精度低但可用。

### 10.2 关键参数（Tesseract）

- 语言包与 `configs/` **必须齐**。缺 `configs/`（尤其 `tsv`）会**静默失败**：
  退出码 0、没有任何输出。**"没报错"又一次不等于"做对了"。**
- 语言包目录要指到**直接包含训练数据的目录本身**，多一层/少一层都会报"打不开数据文件"。

### 10.3 坐标与 DPI（最容易点偏）

> **事故**：测试脚本没声明 DPI 感知 → 取到的窗口坐标被系统虚拟化成逻辑坐标，
> 与物理截图错位 1.5 倍（150% 缩放），表现为"点得偏"。

**定式**：
- 正式程序用 **PerMonitorV2**，全局物理坐标，口径一致
- 临时脚本**必须先声明 DPI 感知**，否则测出来的坐标不可比

### 10.4 窗口与点击

- **Chromium 窗口用 `PrintWindow` 常常全黑** → 需要回退到前台截屏
- **点击必须用系统级输入**（SendInput 一类），消息投递对 Chromium 不可靠
- 系统级输入是**屏幕坐标**、落点取决于谁在最上层 →
  **操作前必须确保目标窗口在前台**，否则会点到别的东西上
- 同名窗口多个 → 取**面积最大**的那个

### 10.5 从 OCR 行到"该点哪一行"

- 按行聚合（TSV 的 `level=4` 行文本可能为空，内容在 `level=5` 的词级行里，
  需按 `(block, par, line)` 分组聚合）
- 拼接词间空格时用 **CJK 规则**（含中文不空格 / 纯西文按间距 / 中英交界空格）
- **排除"题干样行"**（数字开头、问号结尾）—— 否则会点到题干上

### 10.6 自检

- [ ] 用窗口区域截图（与正式程序一致），不用全屏大图
- [ ] 临时脚本声明了 DPI 感知
- [ ] 点击候选排除了题干样行

## 第 11 章 工程化：给"会过期 / 会被外部改动"的东西准备自动补偿

> **这是全文最重要的一章。** 前面讲的都是"怎么让它能跑"，这一章讲"怎么让它不会自己坏"。

### 11.1 一条必须养成习惯的原则

每做完一个"修正"，都问两个问题：

1. **它有没有期限？**（证书、临时数据、会过期的凭据…）
2. **它会不会被外部改动？**（对方更新、文件被重写、状态被清理…）

**只要答"会"，就必须把自动补偿一起写进去。** 不留人工兜底、不留"下次再说"。

### 11.2 典型的"会过期 / 会被改动"的点，与补偿方式

| 点 | 为什么会失效 | 补偿方式 |
|---|---|---|
| 临时数据（下载缓存、索引） | 会被对方定期重写 | **每次运行时重新推导，不缓存** |
| 有效期受硬上限约束的凭据 | 到期即失效 | 到期前**自动续期** + 启动时检查剩余天数 |
| 会被外部清理的工程配置 | 可能被清理/回滚 | **建立后自检**，缺失即自动重建（幂等） |
| 由自己临时改动的系统状态 | 异常退出会残留 | **启动时自愈 + 退出时还原 + 属主令牌**（避免误删别人的） |
| 进程/端口占用 | 多开互相踩 | **单实例互斥**；抢占失败要**如实报错** |
| 白名单类判定 | 对方会加新接口 | **兜底透传/fail-open**，不 fail-closed |
| 调试通道 | 每次都要重新建立 | 启动流程里**显式建立并验证**，失败给出可操作原因 |

> ⚠️ **属主令牌**这个设计值得单独说：临时改动系统状态时，写入的块要带
> **自己的标识**（进程号 + 随机串）。这样程序能判断"这块是不是我写的"，
> **避免误删别人的内容**，也让还原变得精确。

### 11.3 实现要点（可直接抄）

**① 幂等**

"确保存在"的操作必须可以重复执行而不出错：

```csharp
static void EnsureDir(string p) { if (!Directory.Exists(p)) Directory.CreateDirectory(p); }
// 只要能被重复调用，就能放心地在"每次启动"里做自检
```

**② 临时改动必须 try/finally 还原**

```csharp
var saved = Modify();
try { DoWork(); }
finally { Restore(saved); }      // ← 异常路径也必须还原
```

**③ 启动自愈 + 周期自检**

- **启动时**：检查每项"会失效"的前提是否仍成立，不成立就重建
- **运行中**：周期性复查（尤其是自己改动过的系统状态），发现失效立即修复并如实记录
- **退出时**：还原自己改过的一切

**④ 失败要"如实报错"，不要伪装成成功**

> 自检不通过时，**必须回滚并报告**。
> 最糟的是"界面说已启动、其实没接住" —— 用户会在一堆无关的方向上排查很久。

**⑤ 日志：内存缓冲 + 严格限长 + 只在会话内落盘**

高频轮询的接口如果每轮都写日志，很快就会涨到几十 MB。
做法：**内存缓冲 + 单文件严格限长 + 每次启动重建会话日志**。
需要细节时用**开关**打开（默认关闭）。

### 11.4 构建期也有"期限"

- 发布前若改了版本号或任何源文件，**必须先做一次完整重建**（不是增量），
  否则产物里的版本资源还是旧的，打包步骤会直接失败。
- 源文件的编码要一致：**重复的 BOM 会让工程加载失败**。

### 11.5 自检

- [ ] 列出本程序所有"会过期 / 会被外部改动"的点，每一项都有对应的自动补偿
- [ ] 每项补偿都能**被验证**（人为制造失效，看它是否自愈）
- [ ] 异常退出后，系统状态不残留
- [ ] 日志有上限，长时间运行不会涨到 GB 级

## 附录 B 常见坑总表（照这张表排错能省几小时）

| 症状 | 真因 |
|---|---|
| 解出来"有的正常有的乱码" | IV 偏移搞错（多算/少算了一个附加段）——**只有首块乱码** |

| 某些资源解不开，报"校验失败" | 索引文件在**祖先目录**，只查了同级 |
| 匹配命中率低 | 归一化不彻底（标点/全角/空白没洗干净） |
| 选项顺序变了就点错 | 按**序号**映射，而不是按**内容** |
| 未命中时无从下手 | 日志没打 Top-N 候选，分不清"缺数据"还是"阈值问题" |
| 嵌套页面取不到内容 | 帧树没递归（iframe / shadowRoot 漏了） |
| 答到了屏外的常驻题上 | 快照没做"可见且与视口相交"过滤 |
| 点击延迟 0~20 秒随机浮动 | 两条路径**共用一个轮询间隔** |
| 点到了题干上 | 点击候选没排除"题干样行" |
| 排版被超长内容挤坏 | 表格按内容自动分配宽度；长内容应**整行通栏** |
| 打包报 "exe has no version info" | 发布前没做**完整重建**，版本资源未重生成 |
| 工程突然加载失败 | 源文件出现**重复 BOM** |
| 内存日志涨到几十 MB | 高频轮询接口的日志没限长 |
| 界面说"已启动"但功能不通 | 启动自检缺失 / 失败被当成成功 |

## 结语

这份笔记里真正值钱的不是某个格式的解析细节，而是贯穿全篇的两条工程习惯：

> **① 永远先问"我怎么验证它真的生效了"，再去写实现。**
> **② 每做完一个修正，都问它有没有期限、会不会被外部改动；会的，就把自动补偿一起写进去。**

功能写完只是开始，**能自愈的设计才叫完成**。
